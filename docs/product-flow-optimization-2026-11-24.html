01 · Product Essence

产品本质与用户任务

以下判断基于当前源码、现有产品文档与本地页面实跑；未包含真实用户访谈或行为数据，属于待验证的产品假设。

一句话定位

探记是探店达人的“本地经营工作台”：把分散在聊天记录、相册和备忘录里的档期、交付与回款，收束成一条可追踪的订单闭环。

单人多账号纯本地存储工作 × 资金双轨离线优先买断制工具
用户真正要完成的三件事
  1. 今天去哪、先拍哪单：快速看档期、冲突、地点，到店后少切页面。
  2. 这单走到哪、下一步做什么：拍摄、提审、出片、发布都有明确动作。
  3. 这单钱到了没、何时该跟进：定金、尾款、平台到账与催收不遗漏。

03 · Current Flow

当前主链路与断点

工作线与资金线已经并行，这是产品最有价值的设计；问题在于两条线的“完成”定义还没有完全对齐。

工作线
预约建单 / 冲突提醒
拍摄打卡 / 门口照 / GPS
提审记录送审动作
正片 / 副片按配置出片
发布已实现，但容易被待办遗漏
资金线
定金待收 / 已收
尾款私收 / 平台结算
到账确认渠道仅作记录
催收 / 备忘1 / 3 / 7 天
对账流水 / 统计 / 导出
关键断点：当前代码在“正片 / 副片出齐”时就把工作状态判为「已交付」，并不要求「发布」。因此一笔已经出片、尚未发布的订单，会从首页待发片队列消失，并进入「已完结」统计口径。

另一条异常支线是「送审不合格」：当前只记录 pass / fail 标签，不会自动生成“修改后重提”的下一步，也不阻止继续发片与发布。

04 · Recommendations

八项产品流程优化建议

优先级按“数据正确性 → 任务遗漏风险 → 操作效率 → 记录精度”排序；改动面是产品范围判断，不是开发工时承诺。

P0 · 正确性改动面：小—中

01 首次使用先选模式，“开始记录”默认进入工作数据

src/app/storage.js:6, 265-295 · src/app/actions.js:367-369 · src/app/main.js:78
现状
全新环境没有工作数据时默认加载演示数据；工作 / 演示切换入口在统计页数据管理深处。
风险
用户可能把真实预约建在演示里，或以为演示订单就是自己的业务数据；账号配置入口也不易发现。
建议
首次打开提供「开始记录 / 先看演示」二选一。开始记录进入空白工作数据；演示模式保留明显标识。模式切换提升到顶层入口。
验收：新装用户不主动选演示就看不到示例订单；可在 60 秒内完成首个预约；任何页面都能识别当前处于工作还是演示模式。
P0 · 状态闭环改动面：中

02 把“已出片”和“已发布”拆开，未发布必须留在待办

www/logic.js:76-82 · src/app/views/home.js:22, 62-76 · src/app/views/stats.js:74, 95
现状
出齐正 / 副片即返回「已交付」；首页待发片与统计待发片只统计「后期中 / 发片中」。
风险
已出片未发布的订单从首页消失，却被算入完结，用户容易忘记发布。
建议
先做低风险口径修正：交付状态改称「已出片」；新增「待发布」任务口径；首页、订单筛选、统计同时展示。「完结」必须要求已发布。
验收：构造一笔正副片已出、publishedAt 为空的订单，它必须出现在首页待办和待发布计数中；标记发布后才从待办消失并进入完结统计。
P0 · 隐私信任改动面：小—中

03 统一门口照的备份政策，先兑现当前权限承诺

ios/App/App/Info.plist:26 · src/app/storage.js:26, 147-150, 357 · src/app/order-forms.js:91
现状
相机权限说明承诺“照片不包含在导出备份中”；但 JSON 备份原样克隆 orders，订单校验也保留 photoThumb。
风险
用户基于权限文案同意拍摄，却可能在分享 JSON 时一并交出店铺门口照片；换机说明也没有明确哪些媒体会随备份迁移。
建议
推荐 JSON 默认不包含门口照。同步修正导出摘要、导入说明与权限文案，并核查账号头像等其他媒体字段；若未来改为包含，必须显式披露并提供开关。
验收：有门口照的订单导出后，JSON 中不存在该照片的图像数据；导入后订单正常恢复但不出现照片；权限、导出、导入三处文案完全一致。
P1 · 场景效率改动面：小

04 把导航与打卡放回行程场景，减少“进详情再出来”

src/app/views/trip.js:12-22 · src/app/views/home.js:49-59 · src/app/detail.js:162-163
现状
首页今日行有「打卡」，行程行没有；导航只在详情页地点行。
风险
用户按行程页执行任务时，要额外打开详情才能导航或补打卡，到店场景下操作链路过长。
建议
行程 / 今日列表直接提供「导航」；当日未拍订单提供「打卡」。保留详情页完整入口，列表只放高频动作。
验收：从行程页选中一单后，不进入详情即可导航；当日订单可一键打卡并记录时间 / GPS；非当日订单不出现误导性打卡按钮。
P1 · 异常闭环改动面：中

05 送审不合格后生成“修改并重提”，不要只留一个红色标签

src/app/detail.js:149-153 · src/app/order-actions.js:15-25 · src/app/actions.js:208-214
现状
送审结果可标记合格 / 不合格，但工作流下一步与发布守卫不读取该结果。
风险
不合格订单仍可能直接发片、发布；返工原因和重提动作没有形成闭环。
建议
标记不合格后显示「待修改 / 重提」任务，保留本次失败记录；主按钮变为「重新提审」。发布采用软门槛：需合格，或用户明确选择例外并填写原因。
验收：不合格订单出现在待办；重提前保留失败痕迹；未合格且未确认例外时不能发布；例外发布可追溯原因。
P1 · 数据信任改动面：中

06 建立“备份健康”提示，把定期导出从口号变成可见状态

src/app/views/stats.js:100-146 · src/app/export.js:54-68 · src/app/storage.js:317-357
现状
数据仅存本机，JSON 导出完全手动；页面只提示“请定期导出”，没有上次备份时间与备份后变更量。
风险
用户无法判断备份是否过期；换机时也可能误把 .db 当成推荐迁移格式。
建议
统计页显示「上次 JSON 备份 / 此后新增或修改 N 单 / 一键备份」。JSON 明确为换机恢复主路径，.db 定位为归档与技术查看。可提供每周一次应用内温和提醒。
验收：用户能一眼回答“上次备份是什么时候、现在有多少变更没进备份”；备份成功后状态更新；导入预览明确替换范围与恢复方式。
P1 · 高频效率改动面：中

07 新建预约改为“快速必填 + 高级展开”，先保存再补全

www/index.html:581-612 · src/app/order-forms.js:38-80
现状
一个弹层包含商家、地点、账号、类型、结算、服务商、组队、出片要求、时间、价格、定金、联系方式、备注等大量字段。
风险
高频建单像填表；用户在忙时容易拖延记录，或因滚动找不到字段而放弃。
建议
首屏只保留商家、预约时间、总价、出片要求；账号多选与结算方式按需要出现。地点、服务商、组队、联系方式、备注放入「补充信息」，保存后可继续编辑。
验收：常规预约只填 3—4 个核心字段即可保存；冲突提醒仍然触发；多账号订单归属不丢；补充信息不会因为快速保存被清空。
P2 · 财务精度改动面：小—中

08 补记收款允许选择真实到账日期，不再一律记成“现在”

src/app/order-actions.js:28-39, 68-89 · src/app/order-forms.js:120-131
现状
收款与“补记已收”都调用同一逻辑，到账时间固定取当前时刻。
风险
隔天补记会把收入记到错误日期，影响每日实收、月度统计和经营复盘。
建议
收款弹层默认今天，但允许修改实际到账日期；补记场景默认要求确认日期。金额保持定金 / 尾款现有口径，不在本轮扩展复杂分账。
验收：补记一笔昨天到账的尾款，流水与每日统计都落在昨天；撤销仍能精确回滚对应流水。
文案快修：催收备忘

详情页仍写“打开 App 时查看”，原生实际已有本地通知，应统一为“到点本地提醒”。

文案快修：数据库导出

.db 说明不要暗示直接跨设备迁移；明确“JSON 用于恢复，.db 用于归档 / 技术查看”。

口径快修：待发片计数

把“待发布”纳入首页与统计待办，避免用户只看到正 / 副片未出的订单。

05 · Prioritization

建议实施顺序

先修正会造成“数据进错地方、任务被误判完成”的问题，再做高频场景提效，最后扩展记录精度。

阶段范围产品目标进入下一阶段的条件
第一阶段 · P0首次模式选择、发布闭环、门口照备份政策新用户不迷路；未发布订单不消失；备份不违背隐私承诺三项验收用例全部通过，旧数据口径与媒体备份边界无歧义
第二阶段 · P1行程导航 / 打卡、送审返工、备份健康、快速建单减少高频切换；让异常与数据风险可见5 位目标用户完成任务测试，无关键迷路点
第三阶段 · P2收款日期、产品度量基础提升财务记录精度，用数据验证后续迭代确认指标口径与隐私边界后再扩展
推荐的最小可确认版本： 先只做 P0 三项 + 三条文案 / 计数快修。它不需要重构主架构，却能解决首次使用、任务遗漏和备份隐私承诺三个最基础的问题。
06 · Decisions Needed

需要你拍板的六个产品决策

这些不是技术选型，而是产品口径。确认后才有必要进入开发方案设计。

D1 首次打开是否默认进入工作数据？

推荐：是。演示改为主动选择；真实记录与示例数据从第一次打开就分开。

D2 “订单完结”是否必须包含发布？

推荐：是。「已出片」只代表素材交付，「已发布」才代表工作线闭环；两者分别统计。

D3 送审不合格采用硬拦截还是软门槛？

推荐：软门槛。默认要求合格后发布，但保留“例外发布 + 原因”，避免真实业务被工具卡死。

D4 备份提醒是否默认开启？

推荐：先做应用内状态提示，每周温和提醒。不默认增加系统通知，避免与催收、出片提醒争夺注意力。

D5 下一轮开发范围如何收敛？

推荐：P0 + 快修。先验证状态口径与首次使用，再决定是否投入 P1 的场景改造。

D6 门口照是否进入 JSON 备份？

推荐：默认不进入。与当前相机权限承诺一致；账号头像等其他媒体也需要逐项确认，不能沿用模糊的“照片不备份”表述。

07 · Success Metrics

用什么判断优化有效

当前应用只有经营统计，没有产品行为埋点。以下是建议建立的度量口径，不代表现在已经能读取。

北极星指标

每周按时闭环订单数

定义：当周内完成发布，并在约定节点完成收款确认的订单数。它同时反映交付效率与资金闭环，比“新增订单数”更接近用户价值。

驱动指标
  • 首次会话完成首个预约的比例
  • 拍摄到提审、提审到发布的中位时长
  • 超 24h 未出片与待发布订单数
  • 逾期尾款按时跟进比例
  • 7 天内有有效 JSON 备份的用户比例
护栏指标
  • 数据丢失 / 误覆盖事件 = 0
  • 工作与演示数据混淆事件 = 0
  • 错误或重复提醒事件 = 0
  • 隐私模式泄露金额事件 = 0
  • 备份包含未披露媒体事件 = 0
  • 恢复备份失败且不可回退事件 = 0

落地方式建议：先用 5 位真实探店达人做任务测试与访谈，记录耗时、迷路点和放弃原因；确认真实需求后，再考虑本地匿名事件统计。纯本地隐私承诺下，不应未经同意引入服务端行为追踪。

08 · Scope Guardrails

本轮不建议做的事

不是否定长期价值，而是避免在主流程口径尚未稳定时扩大复杂度。

暂不做云同步与强制账号体系

会改变当前纯本地、买断制产品的信任基础，并引入持续服务成本。

暂不做抖音 / 银行自动对账

依赖外部平台接口与授权，稳定性和合规成本高；先把人工确认日期做准。

暂不做批量状态操作

当前“待发布、待返工”口径尚未统一，批量推进容易放大误操作。

暂不做视觉大改版

现有问题主要是任务可见性与状态语义，不是配色和装饰；先修流程收益更高。
